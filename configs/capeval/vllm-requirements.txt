# The vLLM serving stack: pinned standalone requirements, installed into a venv of their own outside the project
# lockfile. Every serving bootstrap (scripts/sdfbase/full22/common.sh f22_serving_venv, scripts/sbatch/serving_probe.sbatch,
# reproduce/02_prepare_model.sh) names that venv after this file's sha256, so any edit here builds a new venv.
#
# Why these versions:
#   * vllm 0.27.x cannot lock in-project: 0.27.0 and 0.27.1 both hard-pin torch==2.13.0, against the base
#     torch==2.11.* cu128 pin, and postdate the exclude-newer cutoff
#   * vllm 0.26.0 is unsatisfiable beside evalplus: vllm 0.26.0 -> nvidia-cutlass-dsl[cu13]==4.6.0 ->
#     nvidia-cutlass-dsl-libs-base 4.6.0 -> protobuf>=6.30.2,<7, while evalplus 0.3.1 -> google-generativeai ->
#     protobuf<6. The protobuf floor arrived in cutlass-dsl-libs-base 4.6.0 (4.5.2 has no protobuf dependency), so
#     vllm 0.25.1 (same torch==2.11.0 stack, cutlass-dsl 4.5.2) is the newest release whose dependencies coexist with
#     evalplus and that runs on driver 570
#   * the PyPI vllm 0.25.1 wheel is CUDA-13-linked (vllm._C_stable_libtorch -> libcudart.so.13), and no official cu128
#     vllm build exists (PyPI: cu13 by default; GitHub releases and wheels.vllm.ai: cpu/cu129/cu130 only). CUDA 12.9
#     binaries run on driver 570 through CUDA 12.x minor-version compatibility (torch 2.11.0+cu129 matmul and
#     vllm 0.25.1+cu129's own rms_norm kernel both execute there), so this file pins the official +cu129 release
#     wheel by direct URL (sha256-pinned, an immutable GitHub asset, which also sidesteps --exclude-newer: that filter
#     drops all of wheels.vllm.ai for lack of upload timestamps) plus the matching pytorch cu129 torch stack. The
#     resolved set includes ninja and the pip-provided nvcc, which flashinfer's JIT needs at engine init
#
# Install, into the job's own venv (never the project venv, which stays lockfile-governed):
#   uv pip install --exclude-newer 2026-08-03T00:00:00Z -r configs/capeval/vllm-requirements.txt
# The cutoff matches the repo's own tool.uv cutoff, and every PyPI pin below predates it; the direct-URL vllm pin is
# exempt by construction and hash-pinned instead. The venv's bin directory must lead PATH when the engine starts:
# flashinfer's JIT looks for ninja and nvcc there at the first engine init.
#
# The torch VERSION agrees with the base lockfile (2.11.0); the local build tag differs (+cu129 here, +cu128 in uv.lock)
# because the official vllm wheel is cu129-built. Folding vllm into the project as a locked group would force that tag
# conflict into uv.lock, so this own-venv requirements file stays its home.
--extra-index-url https://download.pytorch.org/whl/cu129
vllm @ https://github.com/vllm-project/vllm/releases/download/v0.25.1/vllm-0.25.1+cu129-cp38-abi3-manylinux_2_28_x86_64.whl#sha256=9e206f370c934a2d4b6b1f05d3d09708d344e05d80260189ef19f60755709431
# vllm 0.25.1's own torch-stack pins, made explicit as cu129 builds so the resolution is frozen and index-unambiguous:
torch==2.11.0+cu129
torchaudio==2.11.0+cu129
torchvision==0.26.0+cu129
# transformers: pinned BELOW the lockfile on purpose. uv.lock carries 5.15.0 (Nemotron-3-Nano needs it), and a serving
# venv resolved at 5.15.0 breaks vllm 0.25.1's config conversion for gemma-4 (`AmbiguousGlobalPerLayerAttributeError:
# 'head_dim' is a per-layer attribute` from transformers' heterogeneity API, raised in
# vllm/transformers_utils/model_arch_config_convertor.py get_head_size) and engine-core init for qwen35_4b, while 5.14.1
# serves both. Lift the pin only after re-running the served smoke on gemma4e4b AND qwen35_4b
# (tests/test_capeval_driver.py pins it as a deliberate divergence).
transformers==5.14.1
# peft: REQUIRED, pinned to the repo's uv.lock pin (peft 0.20.0, PyPI release 2026-07-28, more than a week old when
# pinned; `[[package]] name = "peft" version = "0.20.0"` in uv.lock). The serving probe's HF+PEFT parity check
# (scripts/sdfbase/serving_probe.py, assertion 4) is a certification check, and a serving venv without peft would run a
# probe whose verdict cannot certify. Every serving-venv bootstrap imports it as a guard, and the verdict refuses without
# reference evidence. peft 0.20.0 declares transformers/torch/accelerate/safetensors/huggingface_hub without upper pins
# that exclude the stack above (uv.lock resolves it beside transformers 5.15.0; 5.14.1 here satisfies its floor).
peft==0.20.0
# evalplus and W&B logging, at the lockfile's pins (evalplus keeps the venv consistent with the project's capeval
# dependency group):
evalplus==0.3.1
wandb==0.28.1
# The vllm-lens steering plugin, for the routing proxy's lens path. vllm-lens' own CI tests vllm 0.19.0, and its
# documented failure mode is capturing nothing without an error, so the serving stack's fail-loud startup assertions
# establish it on a real node (engine init and generate, not just import). A bootstrap failure is recorded and fails
# loud, never a silent skip. If vllm-lens needs a newer vLLM, probe on a node FIRST: do not bump the sha-pinned vllm
# wheel above without that probe.
vllm-lens==1.2.1
